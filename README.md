# AI動画制作支援ツール — 開発ケーススタディ

> AI動画制作スタジオ（社名非公開）の社内向け制作支援ツールを、長期インターンで開発・改善しました。
> 本リポジトリは **成果紹介（ケーススタディ）** です。ツール本体は社内向け非公開リポジトリのため、
> コードは含みません。設計判断とその理由を中心に記載しています。

**担当範囲:** 企画・設計・実装・リリースまで一貫（個人開発 / 1名）
**期間:** 2026年2月〜現在
**体制:** 開発は1人で担当。実際に使う社内ユーザーの声を継続的にヒアリングして反映し、要所で社内エンジニアに相談しながら進めました。

### このページの要点

1. **社員が日常業務で使う本番ツールを、1人で設計から運用まで** — マルチクラウド構成、生成AI 6プロバイダー連携
2. **「どう破られうるか」から逆算したセキュリティ設計** — パスキー必須の多要素認証、権限の自己昇格の防止、同一サイト経由のCSRFまで考慮
3. **障害時とコストの前提を先に決めてから作る** — 機能ごとに fail-open / fail-closed を使い分け、従量課金に自前で上限を置く

## 概要

ノードベースのキャンバス上で、複数のAIモデルを使って画像・動画を生成し、チームで素材を管理・共同編集できるWebアプリです。実際に社員が日常業務で使う **本番ツール** として運用されています。

「社内ツールだから多少雑でいい」とはせず、**認証・権限・コスト上限・障害時の挙動**まで含めて設計しました。本ページはその設計判断を中心にまとめています。

## 技術スタック

| 領域 | 使用技術 |
|---|---|
| フロントエンド | Next.js（App Router）/ TypeScript / React Flow / TipTap |
| バックエンド | Next.js API / Prisma / PostgreSQL / Redis + BullMQ（ジョブキュー） |
| クラウド | Railway（アプリ・ワーカー・DB・Redis）/ Cloudflare R2（オブジェクトストレージ）/ Google Cloud（Drive API・OAuth） |
| 生成AI | 用途に応じて複数の画像・動画生成モデル、LLM を API 連携（6プロバイダー） |
| 認証 | Google OAuth + WebAuthn/パスキー（多要素認証）/ 管理者承認付きデバイス登録 |
| 連携 | MCP サーバー（AIクライアントからの操作口）/ 外部ツールからの Webhook 取り込み |

## アーキテクチャ（概要）

```
                 ┌──────────────┐
  ブラウザ ─────▶│  アプリ       │─── メタデータ ──▶ PostgreSQL
      │          │ (Next.js)    │
      │          │  UI + API    │─── ジョブ投入 ──▶ Redis + BullMQ
      │          └──────────────┘                      │
      │                                                ▼
      │                                        ┌──────────────┐
      │                                        │ ワーカー×4    │──▶ 生成AI API（6社）
      │                                        │ 生成/Drive/   │──▶ Google Drive
      │                                        │ R2/絵コンテ   │
      │                                        └──────────────┘
      │                                                │
      └──── ファイル本体は直接 PUT ──▶ Cloudflare R2 ◀──┘
                （サーバーを経由しない）
```

- **Webアプリ**（Next.js）＝ UI と API。ファイル本体はできる限り通さない
- **バックグラウンドワーカー**＝ 時間のかかる生成処理をキュー（BullMQ/Redis）で非同期実行。用途別に4種類
- **オブジェクトストレージ**（R2）＝ 生成物・アップロード素材を保管、DBにはメタ情報のみ
- 用途ごとに最適なクラウド／APIを選定・連携する **マルチクラウド構成**

# 主に取り組んだこと

## 🔒 セキュリティ

社内ツールとはいえ、**インターネットに公開されたURLで、制作物という資産を扱う** 以上、ログインを突破されたら終わりという作りにはしないことを前提に設計しました。

「何を守るか」「どう破られうるか」から逆算して多層で守っています。

### 想定した脅威と、それぞれに対する対策

| 想定した脅威 | 対策 |
|---|---|
| Googleアカウントの乗っ取り | Googleログインだけでは何もできず、**パスキー（WebAuthn）の2段目ゲート**を必ず通す |
| 第三者が勝手に自分のデバイスを登録する | 新規デバイスは **管理者がメールで承認するまで保留**。承認URLはワンタイム・期限付き |
| クライアント側からの**権限の自己昇格** | 2段目の通過証明を、クライアントが触れるトークンではなく**サーバー署名Cookie**で持つ |
| 他サイトからのCookie付きPOST（CSRF） | ブラウザが付けるヘッダーで判定し、**同一親ドメインの別サブドメインからも遮断** |
| 認証不要パスの前方一致すり抜け | 許可リストは**完全一致か「/」境界のみ**許可し、将来パスの巻き込みを防ぐ |
| 機械用トークンの総当たり | 256bit乱数 ＋ **失敗回数だけ**をIP単位で制限 ＋ 失敗理由を区別しない401 |
| トークンがDBごと漏れる | 平文を保存せず **SHA-256ハッシュのみ** 保管。先頭8文字だけ表示用に保持 |
| ログからの秘密情報流出 | 「ログに出してよいのは先頭8文字とIDだけ」を**コード規約として明文化** |
| アップロード用URLの流出・悪用 | 保存先はサーバーが決定 ／ MIME種別を署名対象に含める ／ 有効期限5分 ／ 事後に実サイズを検証 |
| APIキー漏洩によるコスト爆発 | ストレージの**1日あたりアップロード上限** ＋ 残高枯渇の自動検知通知 |
| 認証器（パスキー）の複製 | 署名カウンタの**逆行を検知して拒否** |
| クリックジャッキング | 認証済み画面を他サイトの iframe に埋め込ませない |
| 開発用スイッチの本番混入 | 本番環境では開発用バイパスを**強制的に無効化**（設定の貼り付け事故対策） |

### 特に設計を悩んだところ

<details>
<summary><b>1. 「2段目を通過した」という事実を、どこに持つか</b></summary>

当初はログインセッションの中（JWTのクレーム）に「パスキー通過済み」フラグを持たせる案でした。これは**自己昇格の穴になる**ため採用しませんでした。クライアント側のAPIから任意のデータをセッション更新処理に流し込めるため、「自分で自分を通過済みにする」余地が残ります。

最終的に、2段目の証明は **サーバーが検証成功時にだけ発行するHMAC署名付きCookie**（httpOnly）にしました。

- 形式は `ユーザーID . 発行時刻 . 署名`
- 署名が合わない／期限切れ／**別ユーザーのもの**は、すべて無効
- 比較は**全文字を必ず走査する形**で行い、一致した文字数から鍵を推測されないようにした
- 有効期間は24時間。パスキー削除などの重要操作では、さらに **直近5分以内の再認証** を要求（step-up認証）

**学び:** 「誰がその値を書き換えられるか」を最初に線引きすると、設計が一つに決まる。

</details>

<details>
<summary><b>2. CSRF対策で「同一サイト」も遮断した理由</b></summary>

一般的なCSRF対策は「別サイトからのリクエスト」を止めます。しかし、**オブジェクトストレージの公開ドメインがブラウザから「同一サイト」と判定される構成**では、そこにHTMLを置かれた場合に素通りしてしまいます。利用者が任意のファイルをアップロードできる以上、ここは想定しておく必要がありました。

さらに、リクエストボディをJSONとして読む処理は Content-Type を検証しないため、フォーム送信を装った攻撃が成立しえます。

そこで、状態を変える操作（POST/PUT/PATCH/DELETE）については、ブラウザが自動で付与するリクエスト元ヘッダーを見て、**別サイトだけでなく「同一サイトの別サブドメイン」からも遮断**しました。自分の画面からの通信は常に「同一オリジン」になるため、正規の利用は影響を受けません。

**学び:** 「自社ドメイン＝安全」ではない。ストレージの公開ドメインは、攻撃者にHTMLを置かれうる場所でもある。

</details>

<details>
<summary><b>3. AIクライアント用の入口だけは、構造上パスキーを通せなかった</b></summary>

Claude などのAIクライアントから操作できる接続口（MCPサーバー）を作りましたが、これは**ブラウザではないためセッションCookieもパスキーも持てません**。独自のトークン認証にせざるを得ず、結果として**この入口だけはパスキーのゲートを迂回します**。

避けられない以上、代わりに最初から次を備えました。

- **失効**（revoke）と**期限**を持つ
- **権限（scope）を read / write / generate に分離** — 「読めるが生成はできない」トークンを作れる
- 平文は発行時の一度しか表示せず、DBには**ハッシュのみ**
- 認証失敗の理由（存在しない／失効済み／期限切れ）を**区別せず同じ401** にし、トークンの存在有無を推測させない
- トークンの先頭に**サービス固有の固定接頭辞**を付け、誤ってコードや設定に貼られた際に**秘密情報スキャンへ引っかかりやすく**した

そのうえで、コードのコメントに「**ここに管理用の画面を足してはいけない / 足すなら認証済みの別パスに置くこと**」という警告を残しました。半年後の自分や後任が同じ罠を踏まないようにするためです。

**学び:** 迂回路を作らざるを得ないときは、「なぜ迂回するのか」「代わりに何で補っているのか」をコードに残す。穴そのものより、穴を忘れることの方が危ない。

</details>

<details>
<summary><b>4. レート制限を「失敗回数だけ」数えるようにした理由</b></summary>

当初はIPアドレス単位で全リクエストを数えていました。しかし組織向けのAIコネクタ経由だと、**全員のリクエストが同じIPから来ます**。これでは正規の利用だけで上限に達し、業務が止まります。

そこで、**IP単位では「認証失敗」だけを数え**（総当たり対策）、認証に成功したリクエストは利用者単位の制限で絞る、という二層に分けました。上限を超えたIPからでも正しいトークンは通りますが、トークンは256bitの乱数なので当て推量は成立しません。

**学び:** 制限の「単位」を間違えると、攻撃者ではなく利用者が止まる。

</details>

### 未対応項目の扱い

セキュリティは「やった対策」より **「やっていない対策を把握しているか」** が重要だと考えています。

未対応の項目は洗い出したうえで、**影響範囲と起こりやすさで優先度をつけて管理**しています。社内の規模や運用実態を踏まえて「今は入れない」と判断したものについても、その理由とあわせて記録しています。

## ☁️ マルチクラウド / クラウドネイティブ

「全部ひとつのクラウドに置く」のではなく、**得意な領域ごとに使い分けて組み合わせる**構成にしました。

| 役割 | 採用先 | 選定理由 |
|---|---|---|
| アプリ・ワーカー・DB・Redis | Railway | GitHubへのマージで自動デプロイ。ワーカーを別プロセスとして増やしやすい。配置は最寄りリージョン（東京）を使用 |
| ファイル保管・配信 | Cloudflare R2 | **データ転送量（エグレス）課金がない**。動画を扱うため、ここが効く |
| 認証基盤・ドライブ連携 | Google Cloud | 社内が既にGoogle Workspace。既存の権限をそのまま使える |
| 生成処理 | 生成AIプロバイダー6社 | モデルごとに得意不得意・価格差が大きく、1社に固定しない |

### 設計判断

<details>
<summary><b>1. ファイル本体をサーバーに通さない（二重ホップの解消）</b></summary>

当初は「ブラウザ → サーバー → ストレージ」とファイルを中継していました。動画は最大500MBあるため、アップロードのたびにアプリサーバーのメモリと帯域を消費します。

これを **「サーバーは“アップロードの許可証”だけを発行し、ファイル本体はブラウザからストレージへ直行する」** 方式（署名付きPUT URL）に変更しました。サーバーはファイルデータに一切触れません。

ただし、許可証を渡す以上、**渡し方を間違えると任意のファイルを置ける穴になります**。次の4点で絞りました。

1. **保存先のパスはサーバーが決める** — クライアント指定を受け付けない（既存ファイルの上書き攻撃を防ぐ）
2. **ファイル種別を署名の対象に含める** — 署名ツールは既定でこれを署名対象から外すため、明示しないと画像のつもりがHTMLを置かれうる
3. **有効期限を5分に短縮** — URLが漏れても悪用できる窓を狭める
4. **アップロード後に実サイズを問い合わせて検証** — 署名付きPUT単体ではサイズ上限を強制できないため、事後確認で担保

**学び:** 「処理を外に出す」最適化は、同時に「信頼の境界を外に出す」こと。性能の話とセキュリティの話は必ずセットになる。

</details>

<details>
<summary><b>2. 障害時に「止める」か「通す」かを、機能ごとに変える</b></summary>

Redisに繋がらなくなったとき、どう振る舞うべきかは機能によって逆になります。

- **レート制限** → **通す**（fail-open）。制限が一時的に緩むことより、ツール全体が止まる方が業務ダメージが大きい
- **認証・権限** → **止める**（fail-closed）。ここを緩めたら対策の意味がない

さらに、実運用で分かったことがあります。**「例外を待つだけでは fail-open にならない」**。使用しているRedisクライアントは、接続できないとコマンドを内部キューに溜めて待ち続けるため、エラーが返ってこず**リクエストごと固まります**。

明示的にタイムアウト（1秒）を置いて初めて、設計通りの「素通し」として機能しました。正常時の処理は1ミリ秒未満なので、十分に余裕があります。

**学び:** 「失敗したらこうする」は、**失敗が“エラーとして返ってくる”前提**に立っている。返ってこない失敗（無応答）が一番こわい。

</details>

<details>
<summary><b>3. 非同期ジョブのリトライ方針を、用途ごとに変える</b></summary>

同じキューの仕組みでも、再試行の設定は揃えませんでした。

| ジョブ | 再試行 | 理由 |
|---|---|---|
| ファイルのストレージ転送 | **5回**（指数バックオフ） | 何度やっても結果が同じ（冪等）。ネットワーク起因の失敗が多い |
| 動画・画像の生成 | **3回** | 失敗が多いが、再試行のたびに課金が発生するため上限を低めに |
| 絵コンテの一括生成 | **1回（再試行しない）** | **1回で数十枚を生成し課金額が大きい**。自動で二重課金させず、失敗は記録して画面から手動で再実行させる |

**学び:** リトライ回数は技術的な設定ではなく、**「失敗したときに誰が何を失うか」** で決まる。お金が動く処理は自動で繰り返さない。

</details>

<details>
<summary><b>4. DBとストレージの責務を分ける</b></summary>

生成物・アップロード素材といったバイナリはすべてストレージに置き、**DBにはURLとメタ情報だけ**を持たせました。DBが肥大化せず、バックアップも軽く保てます。

また、同じ画像を何度アップロードしても重複登録にならないよう、**URLではなく中身のハッシュ値**で同一性を判定しています。URLをキーにすると、同じ画像でも作業空間ごとに別物とみなされ、外部サービス側の登録枠（50件）をすぐ使い切ってしまうためです。

**学び:** 「同じものとは何か」の定義を誤ると、上限のある資源から先に枯れる。

</details>

<details>
<summary><b>5. コストの暴走を、アプリ側で止める</b></summary>

使用しているオブジェクトストレージには**自動の課金停止機能がありません**。APIキーが漏れた場合、気づくまで課金が伸び続けます。

そこで、アプリ側に**1日あたりのアップロード回数上限**（環境変数で調整可）を実装しました。あわせて、生成AI側の**残高切れを失敗エラーから検知してチームへ自動通知**する仕組みも作り、「気づいたら止まっていた／気づいたら請求が来ていた」の両方を防いでいます。

**学び:** クラウドの従量課金は、上限を自分で置かないと上限がない。

</details>

<details>
<summary><b>6. 台数が増えても壊れない形にしておく</b></summary>

共同編集の変更通知を実装する際、アプリが1台である前提のメモリ上の配信にはしませんでした。**2台以上に増えた瞬間、1号機が受けた変更は2号機に繋がっている人に届かなくなる**ためです。

Redisの Pub/Sub を経由させ、どの台で受けた変更でも全台に配る形にしました。Redisは既にキュー・レート制限で使っているため、新しい依存は増えていません。

また、この機能は**環境変数ひとつで丸ごと停止できる**ようにしました（キルスイッチ）。本番で問題が出たら、コードを戻さず設定変更だけで元の動作に復帰できます。

**学び:** スケールアウトは「必要になってから直す」と直せない。今1台でも、**台数に依存しない書き方**を選んでおく。

</details>

<details>
<summary><b>7. プロバイダーごとの差分を1箇所に閉じ込める</b></summary>

生成AIは6社を併用しており、**認証方式すら統一されていません**。同じ会社の中でも、動画生成はトークン認証、素材ライブラリはアクセスキーによる署名認証、と別物でした。

後者は AWS の署名方式によく似ていますが、2点だけ違いがあり（署名スコープの末尾文字列と、署名キーの起点）、**そこを間違えると全リクエストが403**になります。公式ドキュメントの計算例と1ステップずつ突き合わせて特定しました。

こうした差分はすべてアダプター層に閉じ込め、呼び出し側は同じ形で扱えるようにしています。新しいモデルの追加は、アダプターとモデル定義の追加だけで済みます。

**学び:** 「似ているAPI」は、**似ているからこそ差分で詰まる**。既知の方式に寄せて推測せず、公式の計算例で検算する。

</details>

<details>
<summary><b>8. 外部ツールからの取り込みを冪等にする</b></summary>

別の社内ツール（案件フォルダ自動生成）から、Webhookでこのツールへ案件を取り込む連携を作りました。

ネットワーク越しの通知は**再送・二重送信が当たり前に起きる**ため、同じ案件が重複作成されないよう、フォルダIDをキーに**冪等**にしています（2回目以降は作成せず既存を返す）。認証はセッションではなく共有シークレットで行い、**シークレットが未設定なら機能ごと無効化**して、エンドポイントを開けっぱなしにしないようにしました。

**学び:** 分散した仕組み同士の連携では、「1回だけ届く」ことは期待できない。**何回届いても同じ結果**にしておく。

</details>

## 🤖 生成AIの実務統合

- 複数の生成AIモデルを **用途に応じて切り替え可能** な形で組み込み。モデル追加はアダプター層への追加だけで完結する設計に
- **権利面のプリチェック**を実装。静的なNGワード照合に加え、表記揺れや暗喩をすり抜けさせないためLLMによる文脈判定を併用し、リスクを3段階で提示。ユーザーの入力文は**LLMに書き換えさせない**（判定のみ行い、原文を尊重する）方針
- 判定は外部APIに依存するため、**未設定時・失敗時は審査をスキップして通す**（生成を止めない）設計にし、結果はキャッシュして無駄な課金を避ける
- 顔が写った参照画像など、プロバイダー側のフィルターに弾かれるケースは、**自動でキャラクター登録して再送**する仕組みで吸収

# 開発の進め方（プロセス）

機能そのものだけでなく、**どう進めたか**を大切にしました。

### 1. 設計へのこだわりと競合研究
- 既存の類似サービスを実際に触って調査し、優れたUI・機能の「なぜ良いのか」を分解して設計に反映
- 海外で新サービスが出た際もすぐにチェックし、取り入れられる要素を継続的に研究しながら開発
- 「まず簡潔に・最小の変更で最大の効果」を原則に、作り込みすぎない設計判断を意識

### 2. ユーザーフィードバックの反映
- 開発は1人だが、**実際に使う社内ユーザーの声を定例ミーティング等で継続ヒアリング**し、毎回の改善に反映
- 「ここが分かりにくい」「この比率にしたい」といった現場の具体的な要望を、そのまま仕様に落として素早く反映
- **1機能＝1つの小さな変更単位**で、レビュー→確認→反映を細かく繰り返し、**本番で使われているツールを止めずに**継続改善

### 3. 「見えているもの」と「実際に動いているもの」を一致させる
本番ツールを止めずに直すうえで、一番効いた習慣です。

- 外部APIへ**実際に送信される内容を組み立てる処理を、独立した関数に切り出す**
- 変更前（main）と変更後で**送信内容を書き出して差分を取り**、「既存の機能に影響がないこと」を目視ではなく差分で証明してからリリース
- 画面上は正しく見えても送信内容が間違っている、という不具合はこの方法でしか見つけられなかった

### 4. AIの活用と技術的な課題解決・コラボレーション
- 知識が足りない領域は **徹底的に調べ、AI（Claude 等）を"壁打ち相手"** として、設計相談・実装・デバッグ・コードレビューを高速に反復
- 一方で、**製品としての判断・優先順位づけ・ユーザー要望の翻訳・最終確認は自分の責任**で行い、「AIに任せきりにしない／使いこなす」ことを重視
- **根本原因まで理解してから直す**（その場しのぎにしない）を徹底し、同じミスを繰り返さないよう学びを記録する習慣も運用
- 難所は **社内エンジニアにも相談**し、アドバイスをもらいながら実装を前進

# 特に印象に残っている不具合

設計の話だけでなく、**実際に壊れたときに何を学んだか**も残しておきます。

### エラーの分類を文字列で判定していて、データを消していた

参照画像の自動登録が「HTTP 429 / Create asset rate limit exceeded（回数制限）」で失敗する不具合がありました。原因は2つありました。

1. 外部APIの制限が**1分あたり3回**だったのに、画像を連続で登録していた（4枚目で必ず失敗）
2. **より深刻だった方** — エラー文面に `limit` と `exceed` の両方が含まれるため、「登録枠が一杯」と**誤判定**していた。その結果、枠を空けるための処理が走り、**登録済みのデータを毎回1件ずつ削除**していた

枠は50件しかなく、登録には手間も費用もかかるため、「黙って1件消える」は実害が大きい不具合でした。

**直し方:** HTTPステータスを優先して回数制限を判定し、**枠不足の判定より先に**評価するよう順序を固定。あわせて呼び出し間隔を21秒空ける直列化を入れました（並行実行されるワーカーでは、待ち時間の計算だけでは複数が同時に「もう待たなくてよい」と判断して一斉送信になるため、前の処理の完了を待つ形にする必要がありました）。

**学び:** **エラーをメッセージの文字列マッチだけで分類すると、別種のエラーが破壊的な分岐に流れ込む。** 判定の順序そのものが仕様になる。

### 外部クライアントが「対応していない機能」を勝手に検出していた

AIクライアントからの接続が「サインインサービスに登録できませんでした」で失敗する問題がありました。クライアントは接続前に特定のURLを見に来ますが、そこが**ログイン画面へ転送されていた**ため、返ってきたHTMLを「認証機能に対応している」と誤読し、登録を試みて失敗していました。

**正しい挙動は、実装していない機能のURLでは素直に404を返すこと**でした。さらに、片方のURLだけ対処しても、クライアントは**続けて別のURLも確認しに来る**ため、問い合わせ先をすべて洗い出す必要がありました。

**学び:** 「無い」ことを正しく伝えるのも仕様のうち。**曖昧な応答は、相手に勝手な解釈をさせる。**

# 学んだこと

- 実運用に耐えるWebアプリを、**要望→設計→実装→リリース**まで一貫して回す力
- 設計段階からセキュリティを組み込む重要性（**Secure by Design**）。特に「誰がその値を書き換えられるか」から権限設計を決める考え方
- クラウドは**従量課金に自分で上限を置く**必要があり、**障害時にどう倒れるか（fail-open / fail-closed）を機能ごとに決める**のが設計そのものであること
- 複数クラウド／外部APIを **適材適所** で組み合わせる判断
- **AIを開発の相棒として使いこなす力**（調べる・壁打ち・レビュー）と、人（ユーザー・エンジニア）との協働の両立
- 非エンジニア出身でも、**主体的に学び・巻き込み・作り切る**ことでプロダクトを前に進められること
